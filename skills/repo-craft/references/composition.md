# Composition and rendered review

Polish comes from selecting and arranging specific evidence. The goal is a repository people can understand, believe and use.

## Establish a direction

Write three sentences: who is arriving, which real result matters to them, and what they should do next. Identify a likely misunderstanding from the implementation or existing README. Choose an emphasis that resolves it. Retain the existing README and relevant assets outside the target before editing. Inspect the README the host selects rather than assuming the root file is shown.

For a local idea notebook, a short capture-and-find journey can make first use feel effortless. A repository research workspace benefits from exposing the evidence behind a shortlist. The former can be strongest with text; the latter can benefit from a real screen. Neither requires a poster or manifesto.

## Design the reading sequence

| Surface | Opening to try | Evidence to keep nearby | Common failure |
| --- | --- | --- | --- |
| Small CLI | Purpose, minimal command, actual readable output | Runtime requirement and data location | An image forces readers to retype commands |
| Library | Concrete integration in its intended language | Install, expected result, supported environment | API inventory before a useful example |
| Data or model | Question, scoped result, input conditions | Provenance, units, uncertainty, reproduction | Attractive chart without denominator or baseline |
| Visual application | Purpose, material status, one task screen | Caption, fastest demo, setup and limitations | Full desktop screenshot makes the result microscopic |
| Collection or research | Selection criteria and representative item | Navigation and reproduction of selection | An undifferentiated wall of links |

These are hypotheses to adapt, not a universal template. Put costly live setup after a safe offline journey when one exists. Otherwise state access requirements at the first command. A reader should reach a useful action without traversing a brand banner, badge strip, feature wall and architecture diagram.

Use one H1, descriptive H2s and H3s for real subdivisions. Let the host's text and code styles carry most typography. Use bold for material conditions. A concise opening followed by an example often creates stronger hierarchy than a huge image. Use tables for comparisons and short lists for sibling choices. Avoid duplicating the host's outline manually.

Choose one dominant opening visual unless a second answers a different immediate question. Crop around the result while retaining controls, state and limitations needed to interpret it. Remove unrelated navigation or browser chrome only when the crop remains truthful. At the intended width, zoom into the result if the full interface is unreadable. Put commands and interpretation in text. Respect a coherent existing identity; otherwise use crisp white, cool neutral or dark surfaces. Do not impose the same identity on unrelated projects.

A diagram earns space when it explains an actual transformation or boundary. Label conceptual views. A directory tree rarely needs redrawing. Motion earns space when sequence carries information; provide a still or text equivalent. Badges need a current, useful signal, not a numerical quota.

## Build evidence with the presentation

Execute the smallest useful journey with explicitly synthetic input in a disposable copy or isolated data directory. Record source revision, prerequisites, input, exact commands, exit status and output. Declare any redaction or normalization and retain the full safe source. Never improve a result by editing away failures.

Retain editable sources and regeneration steps for kept assets. Use repository-relative links so branches and forks work. Keep licenses and notices. Do not copy third-party branding merely because it was useful for research.

## Review the rendered result

1. Render before and after at the same viewport and theme. Start around 1280 pixels wide and 390 pixels narrow; record actual dimensions. Use the target host when authorized or identify a local Markdown preview as an approximation.
2. Inspect the opening, first example, each changed asset and links into the next step. Confirm purpose, material status and first use are easy to reach. A full-page thumbnail is insufficient.
3. Check light/dark appearance where supported. Confirm picture sources load, transparent artwork has contrast, screenshot text survives scaling and commands remain copyable. Code scrolling can be acceptable; accidental page-wide overflow is not.
4. Follow the first command from a clean copy. Check changed relative links and image targets. Compare captions to actual state. Provide useful alt text and a nearby text account of the result.
5. Fix failures and capture the corrected state. Record concrete changes and keep/skip reasons. Do not infer improved conversions, comprehension or trust from your own visual judgment.

Keep a compact receipt: revision, before/after paths, commands/outcomes, asset provenance, widths/themes, screenshots, defects fixed and unknowns. Stop owned preview processes and verify their ports are gone. External operations follow the publication rule.
