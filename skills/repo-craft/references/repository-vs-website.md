# Repository presentation and website

Repository presentation covers the README, source links, notices, examples and useful metadata encountered on the code host. A Pages website is a separately built and deployed surface. Preparing one does not mean the other exists or is published.

| Need | Repository | Website, if useful |
| --- | --- | --- |
| Purpose and current state | Plain opening sentence and honest status | Reuse the same claims |
| Inspect a result | Example, capture or output file | May reuse the evidence |
| Install or contribute | Runnable instructions and source links | Link to canonical instructions |
| Extensive documentation | Documents can live entirely in the repository | Navigation/search may help |
| Try an interaction | Local instructions or demo link | Only claim interactions that run in this environment |
| Rights and limitations | Preserve notices and specific constraints | Link where readers need them |

## Decide separately

Apply the [three tests](tests-and-proofs.md). A site earns its cost through useful navigation, an audience-specific explanation or interaction. A tiny command line tool with complete usage instructions may need no site.

Record the actual decision: “Skip Pages: one command and its output answer the reader's question,” or “Keep the documentation site: readers need navigation across 30 reference pages.” A request for repository presentation does not automatically request a site.

If selected, use one source for shared claims to avoid drift. Check configured root or project subpath, source links, keyboard use, narrow layout and reduced motion where relevant. A local render proves local rendering only. Deployment is separate under [publication](publication.md).

A custom domain is optional. Never suggest that a static Pages site executes local skills, reads private data or runs commands in the visitor's browser unless that capability actually exists.
